FluentGpu Frame Engine

This document describes how one frame moves through the engine: from a signal change on the UI thread to a present on the display. It also records the changes of this session, why we made them, and the costs that remain.

Text standard: ASD-STE100 (Simplified Technical English). Code names stay in their original form.

1 Goals2 Threads3 Pipeline4 Retained tiles 5 Damage6 Composite7 Changes8 Remaining costs

1Overview and goals

FluentGpu is a GPU UI engine for .NET 10. It compiles with NativeAOT. It draws all UI with Direct3D 12. Wavee is the main application that uses it.

The engine has four design goals:

  1. Cost follows change. A frame that changes a small area must cost a small amount of CPU and GPU time.
  2. Retained GPU work. The engine keeps rasterized pixels in tiles between frames. It draws a tile again only when the content of that tile changes.
  3. Two threads. The UI thread never waits for the GPU. The render thread never waits for layout.
  4. No allocation in the hot path. Steady frames do not allocate managed memory.

The owner measured a failure of goal 1 on the full-screen visualizer stage (3440 × 1440 px, 120 Hz, Adreno X1-85). The values below come from the live log of process 17536.

2Thread model

The engine uses two threads and one mailbox between them.

  • The UI thread runs signals, the reconciler, layout and animation. Then it captures a snapshot of the scene.
  • SceneFramePublisher is a single-producer, single-consumer mailbox with three slots. Each slot holds one snapshot. The newest publication wins.
  • The render thread claims the newest slot. It records the slices, builds the composite frame, submits the D3D12 work and presents on the display tick.

A skipped publication is normal. The UI thread can publish faster or slower than the display. When the render thread skips a publication, the publisher adds the repaint damage of that publication to the next one. A gap does not force a full repaint. Only a target change (first frame, resize, DPI change, device recovery) forces a full repaint at the seam.

The UI thread keeps its dirty bits and its removal ledger until the render thread confirms the consumed sequence. Thus every snapshot describes the change since the last consumed frame.

4Retained tiles

Slices

A slice is a part of the scene that the engine records into its own stream (arena). There are three kinds:

  • Static root. Slot 0. It holds all content that has no reason to be separate.
  • Scroll. The content root of a scroll viewport. The engine records it in content space. The scroll offset is a composite parameter, so a scroll records no bytes.
  • Effect. A node with a composite-time parameter: group opacity, self-blur, edge fade, acrylic, sticky or parallax translation. A repaint boundary is also an Effect slice (section 7c). The engine cuts at most 16 Effect slices (EffectSliceCap) and 16 acrylic slices. Past the cap, the content records inline. The pixels stay the same.

A slice also has a role: Main, Thumb (scroll thumb), Band and PinnedBand (virtual list rows), Layer and Chrome.

Segments

The parent stream holds a CompositeSlice marker at the paint position of each child slice. The markers cut the parent stream into segments. Each segment becomes one row (SliceRow) in the SliceTable. A row has a frame (origin, residual, scale), its painted bounds (ContentBounds) and an identity. The identity uses the node, the role, the segment index and the two markers around it. It does not use the bounds of the child. Thus a child that moves does not change the identity of the parent segments.

Tiles

The TileGrid divides each segment into cells of 1024 × 512 device pixels. The engine cuts each tile surface at the painted bounds of its segment. Tile validity comes from the content. Each turn, every resident tile compares the hash of its last raster with the hash of the content that its segment bytes now describe. If the hashes are different, the tile rasters again.

Budget

The tile budget is clamp(5 × window bytes, 48 MiB, 128 MiB). At 3440 × 1440 px this is about 99 MB. The table requests visible tiles first, then the tiles ahead of a scroll, then the tiles behind it. If the visible tiles of a slice do not fit, the slice is degraded. A degraded slice gets the Direct route: the backend replays it into temporary chunks on every frame. This is correct, but it is expensive.

5Damage

The engine has two damage records. They answer different questions. Do not use one in place of the other.

  • RepaintDamageRegion answers: "Which pixels can be different from the last presented frame?" It holds up to 16 disjoint rectangles in window DIPs. When a 17th rectangle comes, the region merges the pair that adds the least dead area. The region can also be full, with a named reason.
  • FrameInfo.Damage answers: "What must a cached blur sample again?" It is one bounding rectangle over the nodes that moved by transform.

A full region invalidates every tile (InvalidateAll, reason BackgroundOrTheme). A region with rectangles does not invalidate tiles. Tile validity comes from the content hash (section 4). The rectangles feed only the Present dirty-rectangle census.

6Composite submit

The primary window uses one route: the retained-tile composite. It records one command list with three phases. It never reads the back buffer and never copies a render target.

Item kindWhat the composite draws
TilesThe tiles of a segment, as whole-pixel texel loads × alpha × analytic edge feather × rounded clip.
RegionThe tiles of an Effect slice, with its composite clip and layer parameters.
DirectA slice without valid tiles. Phase 2 replays it into temporary chunks.
GroupThe enclosed items, composited into one surface first. Exact group opacity. Cached by content key.
BackdropA frosted surface: a mini-composite of the items below it in its region, blurred with dual Kawase, then tinted.
EraseVideoHoleA DestOut erase. The DComp video visual shows through the hole.

The primary swapchain uses FLIP_SEQUENTIAL with three back buffers (3 × 3440 × 1440 × 4 B = 56.7 MB). Each back buffer keeps its pixels. When the history of a buffer is known, the frame composites only the changed rectangles and presents them with Present1 dirty rectangles. Otherwise the frame clears and composites the whole back buffer, and presents the whole frame. Change (f) gives the details. Popups and detached windows use FLIP_DISCARD and always present whole frames.

7Changes of this session

The log showed that every steady frame repainted the whole window. The causes were in the engine, not in the amount of content. The changes below remove those causes. They do not reduce a cache or a budget.

done(a) Acrylic cache key scoped to its region

FluentGpu.Windows/D3D12/D3D12Device.Composite.cs · BackdropKey, ItemMayPaint

Problem. The cache key of an acrylic backdrop mixed every item before it, anywhere in the window. A spectrum bar on the left changed the key of the panel on the right. Also, one Direct item anywhere made every backdrop uncacheable. Thus all three panels blurred again on every frame.

Change. The mini-composite is scissored to the backdrop region. An item with no pixels in that region cannot change the result. ItemMayPaint now tests the item clip, each tile placement and each prepared surface or chunk against the region. The key mixes only the items that can paint into the region. A Direct item makes the backdrop uncacheable only when it touches the region.

Safety. Two shapes can carry pixels from outside the region into it. The key stays unscoped for them: an earlier backdrop that overlaps the region, and a group that overlaps the region.

done(b) Degraded raster bounded to the painted area

FluentGpu.Windows/D3D12/D3D12Device.Composite.cs · PrepareDirect

Problem. A degraded segment without a clip (for example #root) rastered the whole window into chunks on every frame. This was true also when the segment painted a small area.

Change. The raster area is now the clip ∩ the window ∩ the segment's ContentBounds (moved by the placement offset, plus 1 px). The tile route anchors and cuts its surfaces at the same bounds. Thus the pixels are identical.

done(c) BoxEl.RepaintBoundary: an isolation slice

Dsl/Element.cs · Scene/SceneStore.cs · Scene/SceneRecordingSnapshot.cs · Reconciler/Reconciler.cs · Render/SceneRecorder.cs

Problem. The Field background of the stage has four blobs of about 3800 px. They move on every frame. They were in the root slice, together with the art, the scrim, the bars and the caption. A move of a fraction of a pixel changed the content hash of every root tile. Thus every tile rastered again on every frame, with all the static paint in it.

Change. RepaintBoundary = true on a box makes its subtree an Effect slice without a layer and without a pose. The cut uses the plain-sticky branch of SceneRecorder, which already cut a layer-less Effect slice. The boundary records into its own arena and owns its own tiles. The parent segments keep their identity, because the identity uses the marker node, not its bounds.

Path of the flag. BoxEl.RepaintBoundary → SceneStore sparse column (sets SparsePaint, marks the node record-dirty) → snapshot column → recorder cut. The cut spends the Effect budget. Past the budget, or inside an inline group layer, the subtree records inline. The pixels stay the same.

Test. The gate gate.tiles.repaint-boundary moves a shape under 24 static cells. Inline: 8 tile rasters, all 8 in static tiles. With the boundary: 8 tile rasters, 0 in static tiles.

done(d) BoxEl.RasterScale: low-resolution route

Dsl/Element.cs · Scene/* · Render/SliceRecorder.cs · Seams/Rhi/Composite.cs (CompositeItem.LowResDown) · D3D12Device.Composite.cs (PrepareLowRes) · TileSuite.cs (gate)

Problem. With (c), the Field still rasters about 5 M px of overlapping radial gradients on every frame. Its tiles also hold about 20 MB (one window of BGRA8 at 3440 × 1440). The content is soft. A raster at a lower scale and a bilinear upsample give the same look.

Design.

  1. RasterScale snaps to 1/2, 1/4 or 1/8. The store keeps the factor d (2, 4 or 8) in the boundary column.
  2. SliceRecorder keeps d on the slice record. Place requests no tiles for that slice. It emits a Direct item with LowResDown = d.
  3. The backend replays the segment once, at scale / d, into one scratch surface. It aligns the surface origin to the d grid.
  4. The backend keeps the surface under a content key. A static Field and the backdrops above it stay cached.
  5. DrawSurfaceItem draws the surface with the bilinear Sample path (the path that downsampled blurs already use).

Limit. Use it only for soft content. Text and sharp edges become soft.

Status. Done. PrepareLowRes replays the segment at scale / d into one scratch surface. It keeps the surface under a content key: the segment bytes, the region and d. It uses the kept surface again when no repaint damage reaches the region. A re-render that damage caused changes the key that the backdrops see. Thus a backdrop never uses a blur of old pixels. The Wavee Field uses RasterScale = 0.25. The gate gate.tiles.repaint-boundary shows that a 1/4 boundary composites as one Direct item with LowResDown = 4, and rasters no tiles. Debug and Release builds and all test suites pass.

done(e) Wavee: boundaries on the stage

WaveeMusic/src/apps/Wavee/Shell/Visualizer.UI.cs

  • FieldFace (the stage background and the Field preview) has RepaintBoundary = true.
  • FaceFrame (every visualizer face and the 8 picker previews) has RepaintBoundary = true.
  • Clock.Copy stops when the samples did not change. Before, it bumped the version of 6 series on every tick and caused a record with no pixel change.

done(f) Partial present: FLIP_SEQUENTIAL + Present1 dirty rects

FluentGpu.Windows/D3D12/D3D12Device.PartialPresent.cs (new) · D3D12Device.Composite.cs · D3D12Device.cs · Seams/Rhi/GpuFrameTelemetry.cs (GpuKnockouts.FullPresent) · WindowsApp/Probes/RepaintIdentityProbe.cs (gate)

Problem. On a normal page, the now-playing equalizer ticks at 30 Hz. Its source comment says that each visible change costs a full-window present. The log showed the loop at about 35 fps. The only wake reason was timer, with presents=1052 in 30 s. Each of these frames cleared, composited and presented the whole window to move three small bars. The swapchain was FLIP_DISCARD, which refuses dirty rectangles.

Design.

  1. The primary swapchain is FLIP_SEQUENTIAL. Each back buffer keeps the pixels of the last frame that the engine rendered into it. Popups and detached windows keep FLIP_DISCARD.
  2. After the offscreen phase, PpComputeDirty makes one entry for each tile placement and for each prepared surface. The key of an entry is its identity: the item index, kind and slice, and the tile cell. The signature of a tile placement is the composite parameters of its item plus the tile surface and its raster serial. The signature of a retained surface (group, self-blur, acrylic backdrop, low-resolution boundary) is its content key. The signature of a degraded segment is its stream bytes, unless repaint damage reaches it. An entry without a key gets a new signature on each frame, so it is always dirty.
  3. The engine compares the sorted entries with the entries of the previous frame. The dirty set is the old rectangle and the new rectangle of each entry that changed, appeared or went away. The diff does not use the damage of the recorder.
  4. PpPlanRepaint finds the age of the back buffer: the frames since the engine last rendered into it. The repaint set is the union of the dirty sets of those frames.
  5. The composite pass loads the buffer with PRESERVE. For each repaint rectangle, it clears the rectangle with a FillCopy of the clear colour and draws only the items that touch it. ItemScissor clamps each item to the rectangle. DrawRange skips an item when its footprint is outside the rectangle.
  6. Present1 sends the dirty set of this frame as dirty rectangles. DWM then composes only those rectangles.

Whole-frame route. These frames clear, composite and present the whole window, as before: the first frame, a resize, a DPI change, a clear-colour change, a change of the item structure (set or order), a repaint of 45 % of the window or more, a non-composite submit and a device rebuild. After a stood-down present (the window is covered), the next present is whole, because DWM did not see the changes of that frame.

Limit. A scroll moves every tile in the viewport. Thus a scroll frame usually takes the whole-frame route.

Status. Done, on branch perf/partial-present (fluent-gpu PR #34, stacked on PR #33). The gate partial-present-identity in --repaint-identity renders each static sub-scene at device scales 1.0 to 2.0. It applies six rounds of small changes through the partial route. Then it renders the same state with the whole-frame route. The two captures must be equal: 0 px difference. The GPU time on the owner's machine is not measured yet.

done(g) Compositor clock: no spin when the wait does not block

FluentGpu.Windows/Pal/Win32CompositorClock.cs · FluentGpu.Windows.Tests/CompositorClockSpinTests.cs (new)

Problem. A second Wavee instance showed the fullscreen stage in --fake mode. Only the background moved. The process used about 1.1 cores: 11.3 s of CPU in 10 s. The log showed fast-burst n=2321 spanMs=2.0 and ignored=1083794. DCompositionWaitForCompositorClock returned about 2,300 times in each 2 ms. The tick filter ignored all returns but one for each tick. The waiter thread then waited again at once. Thus the waiter turned into a hot loop. The instance of the owner does not show this problem, but nothing in the engine stopped it.

Design.

  1. After 32 ignored returns in one burst, the waiter parks for about 1 ms between waits. The usual storms of 9 to 21 returns do not reach this limit.
  2. The waiter measures the time that it stays blocked in the export. It uses windows of 250 ms. When a window has 60 waits or more and less than 10 % of the time is blocked, the export does not block. A burst of 1,000 returns has the same result.
  3. Then the waiter starts synthesized ticks. It sleeps on a high-resolution waitable timer for one window period and publishes the tick directly. Thus the host keeps the display rate.
  4. Every 2 s, and after each display change, the waiter tries the export one time. When the export blocks for half a period or more, the waiter uses the real clock again.

Limit. A first version marked the clock unavailable. The fallback of the render thread then used WaitOne(8). At the default timer resolution of 15.6 ms, this gave 64 presents per second. The synthesized ticks keep 120 presents per second.

Status. Done, on branch perf/clock-spin-guard (fluent-gpu PR #35, stacked on PR #34). Three new tests in CompositorClockSpinTests pass: a wait that does not block gives 100 to 130 ticks per second with 2 export calls or fewer per second; a blocking clock and a storm of 20 returns stay on the export.
